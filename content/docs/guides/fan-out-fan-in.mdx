# Fan-out and fan-in (map)

A **map** runs one task many times over a collection. It is an ordinary task
(`kind: horus_map`) that wraps another task, builds one clone of it per item of
the collection (`score[a.txt]`, `score[b.txt]`, ...), runs the clones
concurrently, and collects their outputs into its own single folder output. You
declare the wrapped task once; Horus builds and dispatches the clones at run
time, once the collection is known.

The collection arrives through one of the map task's own inputs, so wiring a
map into a pipeline is ordinary edge wiring: an upstream task feeds the map's
collection input, and any downstream task consumes the map's folder output.
There is no separate gather step to declare.

A map fans out over two kinds of collections:

- **A folder**: the children of a folder artifact, sorted by name. Each clone's
  item points directly at a child file, so fanning out copies no data.
- **A JSON list**: any other input artifact whose content reads as a JSON list.
  Each element is written out as a small file for its clone.

## Collection mode (YAML)

Declare a `kind: horus_map` task. Its `over` field names the input carrying the
collection, `item_input` names the wrapped task's input that receives each
item, and `task:` holds the full wrapped task:

```yaml title="score_batches.yaml"
name: score_batches
kind: horus_workflow

tasks:
  - id: split
    name: Split into batches
    kind: horus_task
    target: { kind: local, working_directory: "./horus-work" }
    runtime: { kind: command, command: "true" }   # produces ./horus-out/batches/*
    executor: { kind: shell }
    outputs:
      - { kind: folder, id: batches, path: "./horus-out/batches" }

  - id: score
    name: Score every batch
    kind: horus_map
    target: { kind: local, working_directory: "./horus-work" }
    over: batches
    item_input: batch
    inputs:
      - { kind: folder, id: batches, path: "./horus-out/batches" }
    outputs:
      - { kind: folder, id: scored, path: "./horus-out/scored" }
    task:
      kind: horus_task
      target: { kind: local, working_directory: "./horus-work" }
      runtime:
        kind: command
        command: "mkdir -p $out && cp $batch/data.txt $out/scored.txt"
      executor: { kind: shell }
      inputs:
        - { kind: folder, id: batch, path: "batch_in" }
      outputs:
        - { kind: folder, id: out, path: "scored_out" }

  - id: summarize
    name: Summarize results
    kind: horus_task
    target: { kind: local, working_directory: "./horus-work" }
    runtime: { kind: command, command: "ls $scored > $summary" }
    executor: { kind: shell }
    inputs:
      - { kind: folder, id: scored, path: "./horus-out/scored_in" }
    outputs:
      - { kind: file, id: summary, path: "./horus-out/summary.txt" }

edges:
  - { source: split, source_output: batches, target: score, target_input: batches }
  - { source: score, source_output: scored, target: summarize, target_input: scored }
```

Run it triggered by the source task:

```bash
horus run score_batches.yaml --trigger split
```

### The map task's fields

| Field | Meaning |
|-------|---------|
| `task` | the wrapped task, in full; one clone of it runs per item |
| `over` | the id of one of the map task's **own inputs**, the one carrying the collection |
| `item_input` | the input id on `task` that each clone receives its item as |
| `max_concurrency` | optional upper bound on how many clones are dispatched at once |

The map must declare **exactly one output**, and it must be a `folder`: that
folder is where every clone's results land.

### Inputs flow to every clone

The wrapped task usually needs more than its item. Any other input declared on
`task` is adopted by the map as one of its own inputs, so you feed it exactly
like you feed the collection, through an edge from upstream or from a root
artifact:

```yaml
  - id: dock
    name: Dock every ligand
    kind: horus_map
    over: ligands
    item_input: ligand
    inputs:
      - { kind: folder, id: ligands, path: "ligands_in" }   # the collection
    outputs:
      - { kind: folder, id: complexes, path: "complexes" }
    task:
      kind: horus_task
      # ...
      inputs:
        - { kind: file, id: ligand, path: "lig.pdbqt" }     # receives each item
        - { kind: file, id: receptor, path: "rec.pdbqt" }   # adopted, shared by all clones
```

Here `receptor` becomes an input of `dock` itself. An edge supplies it once to
the map, and every clone gets a copy on its own target. If you also declare an
input with the same id on the map yourself, yours wins, so you can wire a
clone-shared input differently from how the wrapped task declared it.

The wrapped task's own `id` is optional (it defaults to `<map id>.body`);
nothing uses it directly, because every clone is named `<map id>[<slot>]`.

## How slots and outputs line up

- A **folder** source produces one slot per child, sorted by name, and the slot
  takes the child's name. Items point directly at the children already on the
  map's target, so nothing is copied.
- A **JSON list** source writes each element under the map's working directory,
  and slots are zero-padded indices (`000`, `001`, ...). Each item file keeps
  the suffix of the `item_input`'s declared path.
- Every clone output with a relative path is written inside the map's folder
  output, one directory per slot: `complexes/ligand_A.pdbqt/complex.pdb`,
  `complexes/ligand_B.pdbqt/complex.pdb`, and so on. A downstream task that
  consumes the map's output sees one folder whose subdirectories hold each
  clone's results.

## In Python

Construct a `MapTask` like any other task and put it in the workflow's task
list (or add it with `wf.add_task(...)`):

```python
from pathlib import Path

from horus_builtin.artifact.folder import FolderArtifact
from horus_builtin.executor.shell import ShellExecutor
from horus_builtin.runtime.command import CommandRuntime
from horus_builtin.task.horus_task import HorusTask
from horus_builtin.workflow.horus_workflow import HorusWorkflow
from horus_builtin.workflow.map import MapTask
from horus_runtime.core.workflow.edge import WorkflowEdge

wf = HorusWorkflow(
    name="score_batches",
    tasks=[
        HorusTask(
            id="split",
            name="split",
            runtime=CommandRuntime(command="true"),
            executor=ShellExecutor(),
            outputs=[FolderArtifact(id="batches", path=Path("horus-out/batches"))],
        ),
        MapTask(
            id="score",
            name="Score every batch",
            over="batches",
            item_input="batch",
            inputs=[FolderArtifact(id="batches", path=Path("horus-out/batches"))],
            outputs=[FolderArtifact(id="scored", path=Path("horus-out/scored"))],
            task=HorusTask(
                id="body",  # optional; clones are named score[<slot>]
                runtime=CommandRuntime(command="cp $batch/data.txt $out/scored.txt"),
                executor=ShellExecutor(),
                inputs=[FolderArtifact(id="batch", path=Path("batch_in"))],
                outputs=[FolderArtifact(id="out", path=Path("scored_out"))],
            ),
        ),
    ],
    edges=[
        WorkflowEdge(
            source="split", source_output="batches",
            target="score", target_input="batches",
        ),
    ],
)
```

Pass `max_concurrency=N` to cap how many clones the map dispatches at once.

## Concurrency

Clones run concurrently with each other. Two knobs bound them: the map's own
`max_concurrency` caps that map's fan, and the workflow's
[`capacity`](/sdk/core/workflow#capacity) gates every placement globally,
clones included, so a large fan-out never oversubscribes a machine.

## Skipping and resuming

A map fingerprints its inputs together with the wrapped task's full
configuration, so editing the wrapped command invalidates the map's recorded
result just like editing any other task does. When nothing changed and the
outputs exist, the map skips entirely.

Each clone skips independently through ordinary `skip_if_complete` behaviour
once its own output exists. Clones are registered into the workflow's DAG as
soon as the map builds them, so they serialize with the workflow document: a
run resumed from a stored snapshot sees the previous run's clones, skips the
finished ones, and rebuilds only what is left. Setting
`skip_if_complete: false` on the map propagates to every clone.

## Under the hood

The map is an ordinary DAG node that dispatches its own clones through the
scheduler's machinery: the same transfer step, target pool, and placement
manager that dispatch top-level tasks, with `max_concurrency` bounding this
map's share. Each clone joins the live graph through the runtime `expand(...)`
API behind an ordering-only edge from the map, which is why clones show up in
the dashboard (nested under the map they belong to), in stored workflow
documents, and in resumed runs, where a clone already in a terminal state is
left alone instead of being redispatched.

For a loop that repeats while a predicate holds, see the [Loops](/guides/loops)
guide.
